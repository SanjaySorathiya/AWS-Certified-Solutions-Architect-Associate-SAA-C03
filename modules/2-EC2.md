### **EC2 — Elastic Compute Cloud**

EC2 provides resizable virtual machines in AWS. For the SAA-C03 exam, you must master the exact criteria for selecting the **optimal instance family**, **purchasing option**, **storage configuration**, and **high-availability (HA) architecture**.

---

#### **1. EC2 Instance Families — Technical Selection**

AWS categorizes EC2 instances into specialized families. Select the correct family based on workload requirements:

| Family | Optimized For | Technical Characteristics | Typical Exam Scenarios & Use Cases | SAA-C03 Exam Keywords & Memory Aids |
| :--- | :--- | :--- | :--- | :--- |
| **General Purpose** *(T, M, Mac)* | Balanced compute, memory, and networking. | Burstable performance (T-series using CPU Credits) or fixed performance (M-series). | Web servers, dev/test environments, small/medium databases, and iOS app compilation (Mac). | *\"Balanced resource requirements\"*, *\"bursty workloads\"*, *\"small databases\"*. <br>**M** = **M**ost balanced, **T** = **T**iny/Burstable. |
| **Compute Optimized** *(C)* | High-performance processors. | High CPU-to-memory ratio. Leverages AVX-512 and AWS Graviton processors. | Batch processing, High-Performance Computing (HPC), gaming servers, scientific modeling, and ML inference. | *\"High CPU workload\"*, *\"computational modeling\"*, *\"batch jobs\"*, *\"video encoding\"*. <br>**C** = **C**PU crunching. |
| **Memory Optimized** *(R, X, z, u)* | Rapid delivery of large datasets in memory. | High memory-to-CPU ratio. Includes high-performance RAM and ultra-high memory capacities (up to 24 TiB). | In-memory databases (Redis, Memcached), SAP HANA, real-time big data analytics, and Apache Spark cluster nodes. | *\"In-memory database\"*, *\"large RAM footprint\"*, *\"SAP HANA\"*, *\"real-time processing\"*. <br>**R** = **R**AM-heavy, **X** = e**X**tra RAM. |
| **Storage Optimized** *(I, D, H)* | Local storage performance and density. | High-frequency random I/O or high-throughput sequential reads/writes. NVMe SSD or dense HDD. | NoSQL databases (Cassandra, MongoDB), data warehousing, distributed file systems (Hadoop HDFS), OLTP, and OLAP. | *\"Low-latency local storage\"*, *\"high IOPS\"*, *\"sequential throughput\"*, *\"NoSQL storage\"*. <br>**I** = **I**OPS-focused (SSD), **D** = **D**ense HDD, **H** = **H**DD throughput. |
| **Accelerated Computing** *(P, G, F, Inf, Trn)* | Hardware-accelerated processing. | Co-processors such as GPUs, FPGAs, and specialized ML chips (AWS Inferentia, AWS Trainium). | Deep learning training (P-series), graphics rendering, 3D streaming (G-series), genomic sequencing (F-series), and high-throughput AI inference (Inf-series). | *\"GPU-accelerated\"*, *\"machine learning training\"*, *\"graphics rendering\"*, *\"hardware acceleration\"*. <br>**P/G** = **P**owerful **G**PUs, **Inf** = **Inf**erentia, **Trn** = **Trn**ium. |

##### **Advanced EC2 Instance Features & Security Concepts**

| Concept / Feature | Technical Requirements | Key Constraints / Benefits | High-Yield SAA-C03 Scenario |
| :--- | :--- | :--- | :--- |
| **AWS Graviton** | • ARM64 architecture | • Up to 40% better price-performance compared to comparable x86 instances. | *\"Maximize price-performance or cost-efficiency for Linux-based workloads.\"* |
| **EC2 Hibernate** | • Encrypted EBS root volume<br>• RAM size < 150 GB<br>• Supported OS (Amazon Linux, Ubuntu, RHEL, CentOS, Windows) | • Saves RAM contents to EBS root volume and stops instance.<br>• Cannot use ephemeral Instance Store-backed instances. | *\"Preserve application state across stop/start\"* or *\"avoid long bootstrap/warm-up times on restart.\"* |
| **IMDSv1 vs IMDSv2** | • Link-local address: `169.254.169.254` (IPv4) or `[fd00:ec2::254]` (IPv6 on Nitro) | • **IMDSv1**: Standard HTTP `GET` request. Vulnerable to SSRF.<br>• **IMDSv2**: Session-oriented. Requires a `PUT` request to acquire a session token, then a `GET` with the token in `X-aws-ec2-metadata-token` header. | *\"Mitigate SSRF risks\"* or *\"enforce maximum security for instance metadata access.\"* -> **Enforce IMDSv2-only access (`HttpTokens='required'`)**. |

#### **3. EC2 Storage Options — Block, File, & Object**

Select the correct storage system based on accessibility (block vs. file), throughput, IOPS, and durability.

##### **Amazon EBS (Elastic Block Store) — High-Performance Block Storage**
EBS volumes are network-attached block devices. They are automatically replicated within a single AZ to protect against hardware failure.

| EBS Volume Type | API Name | Max IOPS | Max Throughput | Performance Characteristics | SAA-C03 Target Use Case |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **General Purpose SSD (Latest)** | `gp3` | 16,000 | 1,000 MB/s | Baseline 3,000 IOPS and 125 MB/s included. Scaled independently of volume size. | Boot volumes, virtual desktops, dev/test, and medium-sized databases. |
| **General Purpose SSD (Previous)** | `gp2` | 16,000 | 250 MB/s | Performance scales with size (3 IOPS per GB). Minimum 100 IOPS; burstable up to 3,000. | Older system volumes where performance is tied to disk size. *(Prefer gp3 for cost-performance)*. |
| **Provisioned IOPS SSD (Block Express)** | `io2` | 256,000 | 4,000 MB/s | **99.999% durability**. Sub-millisecond latency. Supports **EBS Multi-Attach**. | High-performance, latency-sensitive critical databases (Oracle, SAP HANA, SQL Server) requiring ultra-high IOPS. |
| **Provisioned IOPS SSD (Standard)** | `io1` | 64,000 | 1,000 MB/s | **99.8% to 99.9% durability**. Supports EBS Multi-Attach. | Older provisioned workloads. *(Prefer io2 for 100x better durability at same price)*. |
| **Throughput Optimized HDD** | `st1` | 500 | 500 MB/s | Low-cost sequential HDD storage. High throughput over IOPS. **Cannot be a boot volume**. | MapReduce, Big Data, log processing, data warehousing, and large sequential file streams. |
| **Cold HDD** | `sc1` | 250 | 250 MB/s | Lowest-cost HDD for infrequently accessed sequential workloads. **Cannot be a boot volume**. | Backup repositories, archives, and cold files accessed rarely. |

##### **EBS Multi-Attach vs. EC2 Instance Store**

| Technical Dimension | EBS Multi-Attach (`io1`/`io2` only) | EC2 Instance Store |
| :--- | :--- | :--- |
| **Storage Type** | Network-attached persistent block storage. | Physically attached block storage. |
| **Latency & IOPS** | Single-digit millisecond latency; up to 256,000 IOPS. | Microsecond-level latency; millions of random IOPS. |
| **Data Persistence** | **Persistent**. Survives instance stop, start, and termination. | **Ephemeral (Temporary)**. Lost on instance stop, termination, or host failure. Survives OS reboots. |
| **AZ Scope** | Restricted to a single AZ. Up to **16 Nitro instances** can attach concurrently. | Local to the physical host inside a single AZ. |
| **Exam Scenario** | Clustered applications requiring shared block storage (e.g., Oracle RAC). *Requires cluster-aware file system (e.g., GFS2)*. | High-speed cache, temp buffers, scratch pads, or distributed replication clusters (e.g., NoSQL). |

#### **4. EC2 High Availability & Auto Scaling**

High availability (HA) is achieved by combining an Application Load Balancer (ALB) or Network Load Balancer (NLB) with an **Auto Scaling Group (ASG)** spanning multiple AZs.

##### **Auto Scaling Group (ASG) Scaling Policies**

| Scaling Policy Type | Operational Mechanics | SAA-C03 High-Yield Use Case |
| :--- | :--- | :--- |
| **Target Tracking** | Scales ASG size to maintain a specific metric (e.g., average CPU utilization) at a target value. | Most standard, metric-driven scaling scenarios. |
| **Step Scaling** | Adds/removes instances in defined "steps" based on CloudWatch alarm thresholds. | Handling sudden, massive spikes in demand with aggressive scaling. |
| **Simple Scaling** | Launches/terminates a fixed number of instances in response to an alarm, then enters a **cooldown period**. | Legacy applications. *(Prefer Step Scaling for new designs to avoid cooldown delay)*. |
| **Scheduled Scaling** | Scales the group size based on a predetermined date and time schedule. | Highly predictable, cyclical, and time-dependent traffic patterns. |
| **Predictive Scaling** | Uses ML to analyze historical traffic, forecast demand, and scale out proactively *before* traffic arrives. | Cyclical workloads with long application bootstrap or initialization times. |

##### **Advanced ASG Features & Operations**

| ASG Sub-system | Operational Mechanics / Workflows | SAA-C03 High-Yield Target |
| :--- | :--- | :--- |
| **ASG Warm Pools** | • Maintains pre-initialized instances in `Stopped` or `Running` state within the ASG. | • Bypasses lengthy boot and application bootstrapping phases.<br>• Reduces scale-out latency from minutes to seconds cost-effectively. |
| **ASG Termination Policy (Default)** | 1. Choose AZ with the most instances.<br>2. Choose instances with the oldest launch template/config.<br>3. Choose instance closest to next billing hour.<br>4. Terminate. | • Optimizes cost and maintains AZ balance.<br>• Use **Instance Scale-In Protection** to exempt critical instances from termination. |
| **ASG Lifecycle Hooks** | • Pauses transition to `InService` or `Terminated` state.<br>• Sends event notifications to SNS, SQS, or EventBridge. | • Runs custom bootstrap or teardown scripts (e.g., state backup, log collection, software installation).<br>• Resume by sending a `CONTINUE` signal. |

#### **5. EC2 Placement Groups — Network & Hardware Layout**

Placement groups control how EC2 instances are physically distributed across host hardware within AWS.

| Placement Strategy | Physical Layout | Maximum Scale & Constraints | Primary SAA-C03 Use Case | SAA-C03 Keywords & Memory Aid |
| :--- | :--- | :--- | :--- | :--- |
| **Cluster** | Instances placed on the **same physical rack** inside a **single AZ**. | Cannot span AZs. Single-point-of-failure (rack failure) risk. | Tightly-coupled HPC, high-throughput distributed databases, and MPI-based workloads. | *\"Ultra-low latency\"*, *\"10 Gbps/high network throughput\"*, *\"node-to-node speed\"*. <br>**Cluster** = **C**lose together. |
| **Spread** | Every instance is placed on **distinct, isolated hardware racks** with independent power and network. | **Max 7 instances per AZ** per placement group. | Critical, highly-available instances requiring complete hardware isolation. | *\"Strict hardware isolation\"*, *\"isolate individual instances\"*, *\"maximum reliability per node\"*. <br>**Spread** = **S**afety first. |
| **Partition** | Instances grouped into logical **partitions**. Partitions do not share racks, but partition can host multiple instances. | **Max 7 partitions per AZ** per placement group. Supports hundreds of instances. | Large-scale distributed big data systems, NoSQL, and rack-aware file systems (Hadoop HDFS, Cassandra, HBase). | *\"Large-scale distributed systems\"*, *\"rack-aware topology\"*, *\"replicated storage partitions\"*. <br>**Partition** = **P**artitioned Scale. |
